# VETAI Proposal Studio — Открытые вопросы

> Вопросы, которые нужно согласовать **до начала реализации**.
> Правило проекта: при неоднозначности записываем вопрос, а не расширяем функционал
> самостоятельно.
>
> Формат: вопрос → почему важен → варианты → предлагаемое решение → статус.
> «Предлагаемое решение» — это рекомендация, а **не** принятое решение.

## Блокирующие (без них нельзя начинать код)

> Статус: блокирующие вопросы закрыты. OQ-01 решён (GigaChat API); OQ-02 решён
> (интерфейс настроек реализован). Актуальные статусы — ниже и в сводной таблице.

### OQ-01. Какой AI-провайдер используем?
- **Почему важно:** ТЗ допускает GigaChat API **или** Yandex AI Studio. От выбора
  зависят авторизация, имена переменных окружения, формат запроса/ответа.
- **Варианты:** (а) GigaChat API; (б) Yandex AI Studio; (в) provider-agnostic с
  заглушкой/mock на этапе разработки.
- **Решение (согласовано):** основной провайдер — **GigaChat API**.
  **Интеграция выполнена** (provider-agnostic адаптер; REST-клиент GigaChat с
  официальной авторизацией OAuth и включённой проверкой TLS; mock-провайдер
  `AI_PROVIDER=mock` для демонстрации и тестов без внешнего API). Слой интеграции
  остаётся провайдер-независимым (REQ-08).
- **Статус:** РЕШЁН (реализовано).

### OQ-02. Как «руководитель» задаёт шаблон структуры КП и прайс?
- **Почему важно:** ТЗ называет роль, но не описывает интерфейс/способ. Это влияет
  на схему данных и объём экранов MVP.
- **Варианты:** (а) редактируемые таблицы в БД через отдельные экраны; (б) статические
  файлы конфигурации/seed-данные; (в) импорт CSV/Excel.
- **Решение (согласовано и реализовано):** управление прайсом и шаблоном через
  минимальный интерфейс настроек — экран **«Настройки»** с вкладками
  «Услуги и цены» и «Шаблон КП» (данные в SQLite: `price_items`, `templates`).
- **Статус:** РЕШЁН (реализовано).

## Важные, но не блокирующие

### OQ-03. Модель версий: когда создавать новую версию?
- **Почему важно:** влияет на схему `proposal_versions` и UX истории.
- **Варианты:** (а) новая версия на каждое сохранение; (б) версии только на ключевых
  действиях (generate / save edit / export).
- **Предлагаемое решение:** (б) — понятнее для демонстрации и истории.
- **Принято на этапе генерации (временно):** новая версия `generated` создаётся
  на каждую генерацию; окончательная политика для действий «редактирование» и
  «экспорт» ещё не определена.
- **Статус:** ОТКРЫТ (частично: генерация создаёт версию за раз).

### OQ-04. Есть ли авторизация/роли в MVP?
- **Почему важно:** ТЗ перечисляет роли, но не требует механизма входа. Это может
  быть «логическая» роль или реальный логин.
- **Варианты:** (а) без авторизации, роли — только в документации; (б) простой логин;
  (в) полноценные роли.
- **Решение (согласовано):** (а) локальный учебный MVP **без авторизации**; роли учтены
  как принципы разделения действий. Для публичной эксплуатации с реальными данными
  потребуется отдельное решение по доступу и безопасности (вне текущего MVP).
- **Статус:** РЕШЁН.

### OQ-05. Точный состав обязательных полей брифа?
- **Почему важно:** определяет REQ-03/AC-01. ТЗ перечисляет «клиент, задача, услуги,
  сроки, бюджет», но какие из них обязательны — не уточняется.
- **Варианты:** (а) все пять обязательны; (б) обязательны клиент/задача/услуги, сроки
  и бюджет опциональны.
- **Решение (согласовано):** (а) **все пять полей обязательны**: клиент, задача,
  минимум одна услуга, сроки, бюджет.
- **Статус:** РЕШЁН.

### OQ-06. Формат «услуг» в брифе: свободный текст или выбор из прайса?
- **Почему важно:** связано с REQ-10 (подстановка цен кодом). Чтобы подставить цену,
  услуги, скорее всего, должны быть выбраны из прайса, а не введены текстом.
- **Варианты:** (а) выбор услуг из прайса (мультивыбор); (б) свободный текст + ручное
  сопоставление; (в) текстовое описание + отдельный выбор позиций прайса.
- **Решение (согласовано):** на этапе №2 использовался **временный каталог учебных услуг
  без цен**; после реализации прайса (реализовано) услуги выбираются из него.
  Временный каталог удалён, чтобы не смешиваться с утверждённым прайсом.
- **Статус:** РЕШЁН.

### OQ-07. Что именно проверяет «защитная проверка перед экспортом»?
- **Почему важно:** ТЗ требует проверку перед экспортом, но не задаёт правила. От набора
  правил зависит сложность и объективность проверки.
- **Варианты:** (а) структурная проверка (разделы шаблона) + сверка цен со snapshot;
  (б) плюс поиск «подозрительных» числовых/обещательных фраз; (в) только структурная.
- **Предлагаемое решение:** (а) как минимум; (б) — как эвристика с пометкой
  «требует ручной проверки», без автоматического удаления.
- **Статус:** ОТКРЫТ.

### OQ-08. Где хранить шаблон КП и прайс при деплое (демо-данные)?
- **Почему важно:** для публикации нужны «учебные/обезличенные данные» (REQ-38). Нужно
  решить, чем наполнять демо и как сбрасывать БД.
- **Варианты:** (а) seed-скрипт с обезличенным прайсом/шаблоном и примером КП;
  (б) пустая БД + инструкция.
- **Предлагаемое решение:** (а).
- **Статус:** ОТКРЫТ.

- **Варианты:** (а) нейтральный учебный шаблон без реальных реквизитов; (б) с

- **Предлагаемое решение:** (а) — безопасно для демо.
- **Статус:** ОТКРЫТ.

### OQ-11. Целевой способ публикации (Streamlit Community Cloud, локальный запуск и т.п.).
- **Варианты:** уточнить у пользователя.
- **Статус:** ОТКРЫТ.

### OQ-12. Данные об исполнителе для разделов «О компании» и подобных?
- **Почему важно:** на этапе качества (REQ-45) разделы без доверенных данных не
  генерируются моделью и помечаются «Требует уточнения». Чтобы автоматически
  заполнять «О компании», нужны **доверенные** данные об исполнителе (название,
  профиль, факты). Их источник и состав в ТЗ школы не заданы.
- **Варианты:** (а) добавить поле-профиль исполнителя (название, краткое описание)
  в «Настройки» и подставлять его кодом; (б) оставить раздел на ручное заполнение
  на этапе редактора; (в) не входит в MVP.
- **Предлагаемое решение:** (а) как минимальное **изменение данных/ТЗ** — новое
  поле-профиль, подставляемое кодом (не моделью). Требует отдельного согласования;
  самостоятельно новые поля не добавляются.
- **Статус:** ОТКРЫТ (предложение, вне MVP без согласования).
