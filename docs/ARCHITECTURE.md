# VETAI Proposal Studio — Архитектура

> Технологический стек — согласованное решение (Python, Streamlit, SQLite, ReportLab),
> а не требование школы. AI-провайдер определён: **GigaChat API** (OQ-01) и
> **интегрирован** (provider-agnostic адаптер + REST-клиент, TLS включён).
> Реализованы каркас приложения, база данных, форма брифа, настройки (прайс и
> шаблон КП) и генерация черновика с программной подстановкой цен и сроков.
> Ручной редактор (REQ-16), проверка перед экспортом (REQ-14), PDF и экран
> истории — впереди.

---

## 1. Обзор

Однопользовательское (на этапе MVP) веб-приложение на Python + Streamlit.
Состоит из UI-слоя, слоя доменной логики, слоя доступа к данным и слоя интеграции
с AI-провайдером. Коммерческие условия (цены, сроки, гарантии) поступают из
**доверенных данных** (прайс, бриф, шаблон), а не от модели.

```
+--------------------------------------------------------------+
|                    Streamlit UI (экраны)                      |
| Бриф | Черновик+редактор | Предпросмотр+PDF | История КП      |
| Настройки (прайс услуг, шаблон КП)                           |
+--------------------------------------------------------------+
             |                    |                 |
             v                    v                 v
+-------------------+  +------------------+  +-----------------+
|  Слой домена      |  |  Слой рендера    |  |  Слой истории   |
|  валидация брифа  |  |  шаблон -> текст |  |  версии, даты   |
|  оркестрация      |  |  PDF (ReportLab) |  |                 |
|  защит. проверки  |  |                  |  |                 |
+-------------------+  +------------------+  +-----------------+
             |                                            |
             v                                            v
+-------------------+                        +-------------------------+
|  AI-адаптер       |                        |  Репозитории (SQLite)   |
|  (provider-       |                        |  briefs, proposals,     |
|   agnostic)       |                        |  proposal_versions,     |
|                   |                        |  price_items, templates |
+-------------------+                        +-------------------------+
             |
             v
+-------------------------------+
|  Внешний AI API               |
|  GigaChat API                 |
|  (ключ из переменных окруж.)  |
+-------------------------------+
```

## 2. Компоненты

### 2.1 UI (Streamlit)
- Четыре экрана из ТЗ школы (REQ-01, REQ-15, REQ-18, REQ-23) плюс экран
  «Настройки» для прайса и шаблона (REQ-29, OQ-02).
- Не содержит бизнес-логики подстановки цен; вызывает доменный слой.
- Состояние брифа сохраняется в `st.session_state` и в БД при ошибках API (REQ-36).

### 2.2 Домен / оркестрация
- Валидация обязательных полей (REQ-02..REQ-05).
- Оркестрация жизненного цикла генерации (раздел 4).
- Программная подстановка коммерческих условий (REQ-10, REQ-12).
- Политика заземления разделов: только `task`/`scope` формирует модель; разделы
  без доверенных данных помечаются «Требует уточнения» (REQ-45).
- Сроки как «число + единица измерения», склонение и канонизация (REQ-44,
  `vetai/deadlines.py`).
- Валидация структуры и защитные проверки (REQ-13, REQ-14).
- Обработка ошибок провайдера и маппинг в понятные сообщения (REQ-35).

### 2.3 AI-адаптер
- Единый интерфейс, скрывающий конкретного вендора (REQ-08).
- Метод вида `generate(structured_input) -> raw_text`.
- Читает ключ из переменных окружения; не логирует ключ (REQ-33, REQ-34).
- Обрабатывает таймаут / лимит / пустой ответ, приводя к доменным ошибкам (REQ-35).
- **Реализация:** `vetai/ai/` — `base.py` (протокол), `errors.py` (доменные
  ошибки), `mock_provider.py` (локальный режим), `gigachat_provider.py`
  (официальный REST API: OAuth Basic→Bearer, `POST /v1/chat/completions`;
  проверка TLS **включена всегда**), `__init__.py` (фабрика по `AI_PROVIDER`).

> **Решение по промпту и заземлению (этапы генерации и качества, REQ-44..REQ-46).**
> Модели передаются **только** разделы, которые она вправе заполнять по данным
> брифа (`task`, `scope` — `MODEL_SECTION_KEYS`). Коммерческие разделы
> (`pricing`, `deadlines`) заполняет код из доверенных данных; цены, сроки и
> бюджет в запрос не передаются вовсе, поэтому модель не может их пересчитать
> или выдумать. Разделы без доверенных данных (`about`, `terms`, `custom_*`)
> **вообще не отправляются** модели — код помечает их «Требует уточнения»
> (`SOURCE_PLACEHOLDER` с пустым текстом). Промпт различает **заказчика** и
> **исполнителя** и запрещает заявления об опыте/заслугах/команде/сертификатах
> исполнителя и о неподтверждённых работах/обязательствах. Промпт — лишь один
> контур защиты; определяющими остаются программная подстановка и политика
> заземления разделов.

### 2.4 Рендер
- Преобразование шаблона + данных в итоговый текст/структуру.
- Коммерческий блок собирается **кодом** из прайса, не моделью.
- **Реализация:** `vetai/services/generation.py` (оркестрация),
  `vetai/services/prompt_builder.py` (промпт и разбор ответа по разделам),
  `vetai/services/commercial.py` (цены/сроки из доверенных данных),
  `vetai/services/text_checks.py` (эвристика «подозрительных» фраз),
  `vetai/services/privacy.py` (обезличивание для логов).
- Генерация PDF (ReportLab) из финальной отредактированной версии (REQ-20, REQ-21) — впереди.

### 2.5 Репозитории (SQLite)
- Доступ к таблицам (раздел 3). Единственное хранилище MVP (REQ-39).
- **Реализация:** `brief_repository`, `price_repository`, `template_repository`,
  `proposal_repository` (КП и версии), `generation_log_repository` (логи).

### 2.6 Импорт прайса из Excel (REQ-47, E-06)
- Способ заполнить **доверенные данные** прайса (REQ-26) помимо ручного ввода.
  Схему данных не меняет: только `INSERT`/`UPDATE` по таблице `price_items`.
- Разделён на **проверку без побочных эффектов** и **применение**:
  `vetai/services/excel_import.py` — разбор `.xlsx` (openpyxl, только чтение,
  `data_only=True`), построение предпросмотра и вызов применения;
  `price_repository.apply_price_import()` — запись **одной транзакцией**
  (commit в самом конце, `rollback` при любой ошибке → частичный импорт
  невозможен).
- **Деньги:** колонка «Цена» в файле — рубли, хранение — целые копейки; перевод
  через `Decimal` (без float), избыточная точность (> 2 знаков) отклоняется.
  Артефакты двоичного представления double округляются до копеек.
- **Сопоставление названий** — регистронезависимое для кириллицы через
  `str.casefold()` в Python (встроенный `lower()` SQLite кириллицу не сворачивает).
- **Политика архива:** сопоставляются только **активные** позиции; совпадение с
  архивной услугой даёт предупреждение и **пропуск** — архив не реактивируется
  автоматически. Услуги, отсутствующие в файле, никогда не удаляются.
- **Безопасность файла:** только расширение `.xlsx`, предел 2 МБ и 5000 строк;
  файлы с макросами (VBA) и повреждённые контейнеры отклоняются; формулы Excel
  не выполняются — читаются только кэшированные значения.
- **Не затрагивает:** брифы, сохранённые версии КП, их `commercial_snapshot` и
  ранее сгенерированные PDF (проверяется тестом).

## 3. Схема данных

## 4. Жизненный цикл генерации КП

```
[Бриф] --(валидация обязательных полей)--> блок, если есть пустые (REQ-03)
   |
   | ok
   v
[Сборка входа] услуги брифа сопоставляются с прайсом (доверенные данные)
   |
   v
[AI-адаптер] вызов провайдера с системным промптом (REQ-06, REQ-09)
   |
   +-- ошибка (timeout/limit/empty) --> понятное сообщение + сохранение брифа (REQ-35, REQ-36)
   |
   v
[Валидация структуры] результат сверяется с шаблоном (REQ-13)
   |
   v
[Подстановка коммерческого блока] цены/услуги вставляются кодом из прайса (REQ-10, REQ-12)
   |
   v
[Сохранение версии] proposal + proposal_version(status=generated) (REQ-22, REQ-25)
   |
   v
[Редактор] менеджер правит текст (REQ-15, REQ-16) -> новая версия (status=edited)
   |
   v
[Предпросмотр] финальная версия (REQ-18)
   |
   v
[Защитная проверка перед экспортом] структура + отсутствие запрещённых данных (REQ-14)
   |        \
   |         \--> провал: экспорт заблокирован, показаны причины
   v
[Экспорт PDF] из финальной версии (REQ-19, REQ-20, REQ-21) -> version.status=exported
```

## 5. Многоконтурная защита от галлюцинаций

**Важно:** системный промпт — лишь **один** из нескольких контуров защиты. Запрет в
промпте **не гарантирует** отсутствие галлюцинаций и не может считаться достаточной
мерой. Поэтому коммерческие условия обрабатываются программно.

Контуры (от слабого к сильному):

1. **Системный промпт** — снижает вероятность, задаёт правила (см. `prompts/proposal_system.md`).
   Не является гарантией.
2. **Структурированный вход** — модель получает обезличенные поля брифа, а не
   произвольный контекст.
3. **Программная подстановка коммерческих условий** — цены, услуги, итоговые суммы
   вставляются кодом из прайса; модель **не формирует** денежные значения (REQ-10, REQ-12).
4. **Валидация структуры** — проверка наличия обязательных разделов шаблона (REQ-13).
5. **Проверка перед экспортом** — блокирующая проверка на запрещённые/неподтверждённые
   данные и на расхождение с доверенными значениями (REQ-14).
6. **Человек в цикле** — менеджер проверяет и редактирует перед выгрузкой (по ТЗ).

Ни один контур в отдельности (включая промпт) не исключает галлюцинации полностью;
защита строится как комбинация программных проверок и человеческой валидации.

## 6. Модель хранения версий

- Каждое КП (`proposals`) связано с одним брифом.
- Текст хранится в `proposal_versions`; каждая значимая операция создаёт запись:
  - `generated` — сразу после генерации;
  - `edited` — после ручного редактирования;
  - `exported` — версия, по которой сформирован PDF.
- Поле `current_version` в `proposals` указывает на актуальную версию.
- `commercial_snapshot` фиксирует, какие цены/услуги были подставлены в этой версии,
  чтобы прошлые КП не «плыли» при изменении прайса.
- PDF формируется из конкретной версии, поэтому всегда воспроизводим.

Точная политика (создавать новую версию на каждое сохранение или только на ключевые
действия) — открытый вопрос OQ-03.

## 7. Логирование

- В `generation_logs` сохраняются промпт и ответ для диагностики (REQ-30).
- **Перед записью** из промпта/ответа удаляются/маскируются персональные данные
  (имена, контакты) и любые секреты (REQ-31, REQ-32).
- API-ключ никогда не записывается в логи (REQ-34).
- Технические логи приложения — отдельно от данных КП.

## 8. Конфигурация и секреты

- Секреты (API-ключ, при необходимости OAuth-данные провайдера) — только через
  переменные окружения (REQ-33).
- Провайдер — GigaChat API (OQ-01), интегрирован. Имена переменных:
  `AI_PROVIDER` (``gigachat`` | ``mock``), `GIGACHAT_AUTH_KEY`, `GIGACHAT_SCOPE`,
  `GIGACHAT_MODEL`, `GIGACHAT_BASE_URL`, `GIGACHAT_AUTH_URL`,
  `GIGACHAT_CA_BUNDLE_FILE`, `AI_TIMEOUT_SECONDS` (см. `.env.example`).
  Значение `AI_PROVIDER=mock` включает безопасный локальный режим без внешнего API.
- Проверка TLS не отключается: допускается лишь указать доверенный корневой
  сертификат Минцифры (`GIGACHAT_CA_BUNDLE_FILE`).
- Файл `.env.example` без реальных значений; `.env` в `.gitignore`.

## 9. Границы архитектуры (что НЕ проектируем в MVP)

- Нет слоя авторизации/ролей (REQ-37; OQ-04 решён: локальный учебный MVP без авторизации).
- Нет интеграций с внешними системами (CRM/почта/оплата).
- Нет фоновых задач, очередей, многопользовательской синхронизации.
