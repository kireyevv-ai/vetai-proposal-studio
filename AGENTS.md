# AGENTS.md — Правила работы над VETAI Proposal Studio

Этот файл описывает правила для последующих сессий OpenCode в этом репозитории.
Читай его перед любыми изменениями.

---

## 1. О проекте

VETAI Proposal Studio — учебный AI-конструктор коммерческих предложений для сервисной
компании. Сценарий: бриф → проверка полей → генерация черновика через AI → ручное
редактирование → экспорт PDF → история КП.

Текущий статус: создана проектная документация; реализованы каркас приложения,
база данных SQLite и форма брифа. Генерация через AI, редактор, экспорт PDF и история
КП ещё **не реализованы** — соответствующие экраны сообщают о своём статусе.

---

## 2. Главные правила (обязательны)

1. **ТЗ школы — главный источник требований.** Не выдумывай требования.
2. **Не добавляй новые бизнес-функции** по своей инициативе.
3. **Не реализуй без согласования:** роли, авторизацию, CRM, оплату, почтовые и
   мессенджер-интеграции, аналитику и прочие расширения.
4. **Неоднозначность → открытый вопрос.** Записывай вопрос в `docs/OPEN_QUESTIONS.md`,
   а не расширяй функционал самостоятельно.
5. **Разделяй:** требования школы / технические уточнения / потенциальные улучшения.
   Тип помечается в `docs/REQUIREMENTS.md` (`Школа`, `Тех`, `Улучшение`).
6. **Не изменяй и не создавай код приложения без явного подтверждения пользователя.**
7. Каждое требование имеет идентификатор `REQ-NN`. Новые требования — только с новым ID
   и ссылкой на источник.
8. **AI-провайдер определён:** основной — **GigaChat API** (см. `docs/OPEN_QUESTIONS.md`,
   OQ-01, статус «Решён»). Интеграция ещё не выполнена. Не подключай API и не добавляй
   других провайдеров без согласования; слой интеграции держи провайдер-независимым
   (REQ-08).

---

## 3. Защита от галлюцинаций — ключевой принцип

- **Системный промпт — только один уровень защиты.** Никогда не утверждай, что запрет
  в промпте полностью исключает галлюцинации.
- Коммерческие условия (цены, сроки, гарантии, обязательства) должны подставляться
  **программно из доверенных данных**, а не формироваться моделью.
- Обязательны: программная подстановка цен (REQ-10, REQ-12), валидация структуры
  (REQ-13) и блокирующая проверка перед экспортом (REQ-14).
- Модель **не вправе** придумывать цены, сроки, гарантии и коммерческие обязательства.

---

## 4. Безопасность и приватность

- API-ключ хранится **только** в переменных окружения / на сервере (REQ-33).
- Никогда не коммить секреты; `.env` в `.gitignore`, есть `.env.example` без значений.
- Логи промптов/ответов **без персональных данных** и без секретов (REQ-30..REQ-32).
- PDF не должен содержать ключей и персональных данных.
- Использовать только учебные/обезличенные данные (REQ-38).

---

## 5. Стек и провайдер

Стек согласован: Python, Streamlit, SQLite, ReportLab (ReportLab — для будущего
экспорта PDF, пока не используется). AI-провайдер — **GigaChat API** (OQ-01); интеграция
запланирована на следующем этапе. Держи слой интеграции провайдер-независимым (REQ-08).

---

## 6. Документация и процесс

- Документы: `docs/PROJECT_PASSPORT.md`, `docs/REQUIREMENTS.md`, `docs/ARCHITECTURE.md`,
  `docs/DELIVERY_PLAN.md`, `docs/OPEN_QUESTIONS.md`, `prompts/proposal_system.md`.
- При изменении требований обновляй `REQUIREMENTS.md` и, при необходимости, трассировку
  и критерии приёмки.
- Новые вопросы — в `OPEN_QUESTIONS.md` со статусом.
- Предложения сверх ТЗ — в раздел «Отклонения и расширения» файла `OPEN_QUESTIONS.md`.

---

## 7. Git

- Не коммить и не пушить без явной просьбы пользователя.
- Перед коммитом проверяй `git status` и `git diff`; не добавляй секреты.

---

## 8. Прежде чем писать код

1. Прочитай `docs/OPEN_QUESTIONS.md` — блокирующие вопросы должны быть закрыты.
2. Дождись явного подтверждения пользователя.
3. Сверься с `docs/ARCHITECTURE.md` и `docs/DELIVERY_PLAN.md`.
4. Следуй типу требования, не расширяй объём MVP.

---

## 9. Definition of Done

- Реализованное соответствует `REQ-NN` и не выходит за границы MVP.
- Защитные проверки (цены, структура, экспорт) на месте и протестированы.
- Нет секретов/PII в коде, логах, репозитории.
- Обновлена документация при отклонениях.
