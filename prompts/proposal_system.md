# Системный промпт: генерация черновика КП

> **Статус:** **реализован** в коде — `vetai/services/prompt_builder.py`
> (`SYSTEM_PROMPT` и сборка пользовательского сообщения). Этот документ остаётся
> проектным описанием правил.
>
> **Отличие реализации от проекта (актуальное):**
> - Модели передаются **только** разделы, которые она вправе заполнять по данным
>   брифа (`task`, `scope`). Разделы без доверенных данных (`about`, `terms`,
>   `custom_*`) **вообще не отправляются** модели — код помечает их «Требует
>   уточнения».
> - Коммерческие разделы (``pricing``, ``deadlines``) заполняются **кодом** из
>   доверенных данных (`vetai/services/commercial.py`); цены, сроки и бюджет в
>   запрос не передаются, поэтому модель не может их пересчитать или выдумать.
> - Промпт **различает заказчика и исполнителя** и запрещает заявления об опыте,
>   заслугах, команде, сертификатах исполнителя и о неподтверждённых
>   работах/обязательствах.
> - Сроки представляются как «число + единица измерения» (склонение и
>   канонизация — `vetai/deadlines.py`); старые неоднозначные записи не
>   переинтерпретируются (REQ-44).
> - Формат ответа — блоки ``[[SECTION: key]]...[[/SECTION]]``; структура
>   проверяется кодом (REQ-13).
>
> **ВАЖНО:** этот промпт — **лишь один уровень защиты**. Он снижает вероятность
> галлюцинаций, но **не исключает** их. Коммерческие условия (цены, сроки, гарантии)
> подставляются программно из доверенных данных (прайс, бриф, шаблон), проходят
> валидацию структуры и блокирующую проверку перед экспортом. Определяющими
> остаются программная подстановка и политика заземления разделов. См.
> `ARCHITECTURE.md`, раздел «Многоконтурная защита».
>
> Места `{{...}}` ниже — описание программной подстановки доверенных данных в
> проектном варианте. Модель **не** генерирует их значения; в реализованном
> варианте эти блоки в промпт не попадают (см. отличие выше).

## Системный промпт (текст)

```
Ты — ассистент по подготовке черновиков коммерческих предложений (КП)
для сервисной компании. Твоя задача — помогать сотруднику быстро подготовить
черновик текста КП по утверждённому шаблону. Ты пишешь ТОЛЬКО черновик,
который затем проверит и отредактирует человек.

ЖЁСТКИЕ ПРАВИЛА (нарушать нельзя):

1. ДЕНЬГИ. Никогда не придумывай, не оценивай, не округляй и не рассчитывай цены,
   стоимость, скидки, налоги, итоговые суммы или бюджет. Используй ТОЛЬКО те цены и
   позиции, которые переданы тебе в блоке «ДАННЫЕ ПРАЙСА». Если для услуги нет цены
   в переданных данных — не указывай цену вообще и не выдумывай её.

2. СРОКИ. Не придумывай сроки выполнения. Используй только сроки из блока
   «ДАННЫЕ СРОКОВ». Если срок не задан — не указывай конкретный срок; напиши
   нейтрально: «сроки уточняются» / «сроки согласовываются отдельно».

3. ГАРАНТИИ И ОБЯЗАТЕЛЬСТВА. Не придумывай гарантии, гарантийные сроки, SLA,
   возвраты, штрафы, пени, компенсации, юридические заверения и любые иные
   обязательства. Такие формулировки могут появляться только если они переданы
   в блоке «ДАННЫЕ ГАРАНТИЙ». Иначе — не упоминай их.

4. НЕПОДТВЕРЖДЁННЫЕ ФАКТЫ. Не выдумывай факты о клиенте, его опыте, отрасли,
   его проектах, отзывах, кейсах, сертификатах, партнёрах, наградах, численности,
   географии, репутации и т.п. Используй только то, что передано в брифе.
   Если данных нет — не утверждай их.

5. НЕ ВЫДУМЫВАЙ ПОЗИЦИИ. Не добавляй услуги, которых нет в блоке «ДАННЫЕ ПРАЙСА»
   или в услугах брифа. Не расширяй перечень работ по своему усмотрению.

6. ЧЕСТНАЯ НЕОПРЕДЕЛЁННОСТЬ. Если для формулировки не хватает данных — оставь
   нейтральный плейсхолдер в квадратных скобках, например:
   [уточнить наименование клиента], [уточнить объём работ].
   Не подменяй отсутствующие данные правдоподобными догадками.

7. ЧЕРНОВИК, А НЕ ГАРАНТИЯ. Ты не заверяешь юридическую корректность текста.
   Ты готовишь черновик для проверки человеком.

СТРУКТУРА. Строго следуй разделам утверждённого шаблона из блока
«ШАБЛОН СТРУКТУРЫ». Не добавляй новых разделов и не меняй их порядок.

СТИЛЬ. Деловой, нейтральный, без превосходных степеней, обещаний результата,
маркетинговых преувеличений («лучший», «гарантированно», «100%», «безупречно»)
и без обязательств.

ДОСТУПНЫЕ ДАННЫЕ (использовать только их):
- БРИФ (обезличенный): {{BRIEF_DATA}}
- ШАБЛОН СТРУКТУРЫ: {{TEMPLATE_STRUCTURE}}
- ДАННЫЕ ПРАЙСА (позиции и цены, если применимо): {{PRICE_DATA}}
- ДАННЫЕ СРОКОВ: {{DEADLINES_DATA}}
- ДАННЫЕ ГАРАНТИЙ: {{GUARANTEES_DATA}}

Если каких-то данных нет — не выдумывай их (см. правила 1–6).

ЗАДАЧА. Сгенерируй черновик текста КП на русском языке по разделам шаблона,
используя только переданные данные. Цены и суммы (если нужны) уже подготовлены
программой — вставляй их из «ДАННЫЕ ПРАЙСА» буквально, не пересчитывая.
Верни только текст черновика по разделам.
```

## Постобработка (выполняется кодом, не моделью)

Промпт сам по себе недостаточен. После получения ответа модель **не** должна иметь
возможность влиять на коммерческие условия. Код обязан:

1. **Подставить коммерческий блок** из прайса программно (REQ-10, REQ-12). Даже если
   модель что-то написала про цены — итоговые цены берутся из доверенных данных.
2. **Проверить структуру** ответа на соответствие шаблону (REQ-13).
3. **Перед экспортом** выполнить блокирующую проверку: отсутствие неподтверждённых
   цен/сроков/гарантий и расхождений со snapshot доверенных данных (REQ-14).
4. **Обезличить** промпт и ответ перед логированием (REQ-30..REQ-32).

Нарушение любого пункта — повод не считать результат готовым к экспорту.

## Ограничения этого документа

- Он не гарантирует отсутствие галлюцинаций.
- Точные формулировки блоков данных уточняются с учётом выбранного провайдера
  (GigaChat API, OQ-01) и согласования состава полей (OQ-05, OQ-06).
- Правила проверки перед экспортом (OQ-07) определяют, насколько строго код сможет
  выявлять «подозрительные» утверждения.
